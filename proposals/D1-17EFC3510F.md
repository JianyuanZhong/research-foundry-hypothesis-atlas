## 1. Deterministic source-to-panel matching contract

### 1.1 Sealed source rows and identity

Before any panel opens, write `source_unit_manifest.jsonl` containing one row for every emitted unit, including rejected/boundary diagnostics. Each row contains protocol version, source snapshot/hash, source table, `(subject_id,hadm_id,note_id)`, reciprocal-chain identifier, zero-based unit ordinal, source byte offsets or stable source-row digest, `R_store`, full source assertion envelope, and a rejection code if applicable. The canonical unit is

`U=(subject_id,hadm_id,source_note_id,reciprocal_chain_id,unit_ordinal)`.

Source parsing uses UTF-8, Unicode NFC only for the extractor, ASCII LF, outer-whitespace trimming exactly as specified, null distinct from empty string, and UTC-naive timestamps serialized with six fractional digits. Source text is retained byte-for-byte and never overwritten. Rows are sorted only by the declared key `(storetime,charttime,note_seq,note_id)` with nulls last and serialized note key as final tie-break. Duplicate physical rows remain until key audit.

### 1.2 Panel record schema

Every H1/H2/H3 or bridge panel output is a separate immutable record in `panel_output_manifest.jsonl` with exactly `(panel_id,lane_id,reader_id,admission_key,unit_id,assertion_tuple,workflow_availability_code,actionability_code,output_status,template_hash,protocol_hash,received_at,record_hash)`. A panel record without an exact `unit_id` is not matched by text; it is `PANEL_KEY_MISSING` and becomes `UNKNOWN`/`NONRESPONSE` in the compatible set. Reader IDs and lane IDs are pseudonymous workspace identifiers, not responsible-team claims.

The assertion tuple is the exact frozen nine-field tuple `(unit_id,target_cluster,action_modality,due_interval,polarity,recipient,responsibility,replacement,conflict)`. Values are coded values, `ABSENT`, or `UNKNOWN`; no synonym, vote, semantic similarity, fuzzy text match, provider inference, or analyst override is allowed.

### 1.3 Pure matching algorithm and one-to-many behavior

For each admission and lane, match only on the serialized five-part unit key `(subject_id,hadm_id,source_note_id,reciprocal_chain_id,unit_ordinal)`. First enforce admission-key equality; subject-only or note-text-only matches are forbidden. Then compare the five fields `(target_cluster,action_modality,due_interval,polarity,(recipient,responsibility))` exactly. Identical coded values are `MATCH`; `ABSENT` versus any non-`ABSENT` is `NONMATCH`; distinct coded values are `NONMATCH`; `UNKNOWN` retains both compatible `MATCH` and `NONMATCH` states with reason `UNKNOWN_WILDCARD`. `replacement` and `conflict` are independent and never collapsed.

The matcher emits an ordered match-set, not a selected winner: `DUPLICATE_RESTATEMENT` only when `U` and all assertion fields are identical; `DISTINCT_UNIT` for distinct identities; `MATCH`, `NONMATCH`, or `AMBIGUOUS_MATCH` for candidate links; and `PANEL_KEY_MISSING`, `PANEL_DUPLICATE_KEY`, or `PANEL_UNEXPECTED_UNIT` for panel-contract failures. A one-to-many mapping is retained as all valid states with a proof trace. It is never resolved by majority, route, bridge success, or favorable selection. A duplicate panel key is an error that produces adverse-compatible `UNKNOWN`, not silent deduplication.

Write `match_manifest.jsonl` sorted by `(admission_key,unit_id,lane_id,reader_id,match_state,assertion_hash)` and `match_manifest.sha256`. Each output row records all compared values, null/empty/`UNKNOWN`/`ABSENT` distinctions, candidate cardinality, reason, and source/panel hashes. Reordering source rows, panel rows, or input partitions must yield byte-identical manifests. Any key collision, omitted candidate, malformed canonical JSON, or row-count mismatch fails closed before route/bridge labels.

## 2. H3 assertion-support rerun reproducibility certificate

H3 is a fixed assertion-support challenge, not a truth oracle and not a new sample. Its roster, q=`1/3` rounded-down challenge reservation, admission ceiling, and inherited challenge workload are frozen before labels. The compiler writes `h3_input_manifest.json` containing the sorted challenge admission/unit roster, source unit hashes, canonical DS hashes where used, challenge allocation, panel lane, prompt/template hash, codebook hash, protocol hash, source snapshot/hash, software/container digest, locale/time-zone settings, random seed, and exact input-file hashes. No label, route, disagreement, bridge state, or post-label outcome enters the roster or seed.

Define the deterministic H3 seed as `SHA256(protocol_hash || source_snapshot || sorted_roster_hash || h3_template_hash || codebook_hash || declared_seed_string)`, interpreted as a fixed unsigned integer. Any pseudorandom operation uses a named algorithm/version, that seed, and stable sorted keys; no wall clock, process ID, thread order, hash-table iteration, or system locale is permitted. H3 prompt order is the manifest order, and panel response serialization uses the common canonical serializer.

After each H3 run, write `h3_output_manifest.jsonl`, `h3_certificate.json`, and `h3_certificate.sha256`. The certificate must include input-manifest hash, output-manifest hash, every per-record output hash, roster count, expected/observed cardinalities, algorithm/library/container versions, seed derivation inputs, execution timestamp as provenance only, and `rerun_status`. A clean rerun means a fresh process reading the same immutable snapshot and sealed input manifest produces identical ordered output bytes and identical output hash. Run H3 twice before opening the clinical interpretation; compare bytes and hashes, not rounded summaries. `RERUN_IDENTICAL` is required. `RERUN_MISMATCH`, missing output, changed roster, changed prompt/codebook, or changed source hash yields `H3_REPRODUCIBILITY_FAILURE` and `NO_SELECTION` for the affected H3-dependent claim; no rerun may be discarded or hand-reconciled. A successful certificate establishes computational reproducibility only, not correctness, clinical appropriateness, workflow delivery, safety, benefit, or causality.

## 3. Eight mutually exclusive workflow availability codes

Workflow availability is a source-evidence status for each required workflow field (and an admission-level aggregate); it is not a clinical action, team identity, or outcome. The complete fixed codebook is:

1. `PRESENT_IN_AVAILABLE_SOURCES`: the required field is present in an allowed source row, passes exact key and type checks, and has an unambiguous value;
2. `NOT_PRESENT_IN_AVAILABLE_SOURCES`: the field was searched in every predeclared allowed table/archive member and no row/field exists for that required value; this is a documented absence from the configured sources, not evidence that the event did not occur;
3. `UNKNOWN`: an allowed source contains a relevant row/field or the source is present, but value interpretation, scope, or temporal meaning cannot be determined from available data;
4. `CONFLICTING_AVAILABLE_SOURCES`: two or more allowed source values for the same exact key/time field conflict and no frozen precedence resolves them;
5. `TIMING_UNRESOLVED`: a relevant value exists but required ordering relative to `D` or another locked clock cannot be established because a required timestamp is null, malformed, or contradictory;
6. `KEY_UNJOINABLE`: a potentially relevant row exists but cannot be joined by the exact declared key, such as missing `hadm_id` or missing `(subject_id,note_id)` components; subject-only or text-only resemblance is insufficient;
7. `SOURCE_UNREADABLE`: the allowed source/member is present but the row, field, archive member, or packet fails decoding/integrity/schema validation;
8. `NOT_APPLICABLE`: the field is outside the predeclared workflow construct for that record by the frozen design, rather than missing evidence.

Precedence is deterministic and applied per field before any aggregation: `SOURCE_UNREADABLE > KEY_UNJOINABLE > CONFLICTING_AVAILABLE_SOURCES > TIMING_UNRESOLVED > UNKNOWN > PRESENT_IN_AVAILABLE_SOURCES > NOT_PRESENT_IN_AVAILABLE_SOURCES`, with `NOT_APPLICABLE` used only when the field’s design applicability predicate is false. Thus a present row with an uninterpretable value is `UNKNOWN`, whereas exhaustive absence after successful search is `NOT_PRESENT_IN_AVAILABLE_SOURCES`; neither is recoded to the other. Conflict and timing states are never favorable. The admission workflow class in atom `g` is computed from the sorted vector of field codes under a frozen lookup table whose hash is included in the protocol manifest. No workflow code is inferred from `author`, `admit_provider_id`, `curr_service`, or ICU exposure as accountability; those remain proxies exactly as inherited.

For every field, emit `availability_search_manifest.jsonl` with allowed source paths, archive members, schema hashes, exact key, search predicate, rows inspected, matching row IDs, clock fields, and final code. If a source is outside the configured catalog, use `NOT_PRESENT_IN_AVAILABLE_SOURCES` only for the declared available-source universe and separately record `SOURCE_OUTSIDE_CONFIGURED_UNIVERSE`; never describe that as evidence of clinical absence. `UNKNOWN` is retained in all compatible states and is adverse-compatible where decision relevant.

## 4. Actionability precedence and availability separation

`eligibility_code` and `actionability_code` are mandatory separate fields. Eligibility is sealed before any label and requires the inherited unique admission, unique canonical `U`, reciprocal pre-`D` chain, non-null `R_store<D`, complete structural target envelope, exact admission join, and unique/nonempty canonical DS with non-null `storetime`; detail ambiguity remains observable rather than deleted.

For an eligible pair, apply exactly this first-match state precedence, with no overlapping states:

`DS_UNREADABLE` -> `DETAIL_AMBIGUOUS` -> `NONRESPONSE` -> `NA_NO_TARGET` -> `NA_NO_ACTION` -> `TIMING_UNRESOLVED` -> `TARGET_CONTRADICTED` -> `SUPERSEDED_EXPLICIT` -> `ACTIVE_PARTIAL` -> `ACTIVE_EXACT` -> `BRIDGE_INCONCLUSIVE`.

The structural branch is `NA_NOT_ELIGIBLE` whenever eligibility is false. `NA_NO_TARGET` and `NA_NO_ACTION` are permitted only for explicit structural absence established by the locked parser and are excluded from the target-preservation denominator while reported in the all-opportunity accounting. `DS_UNREADABLE`, `DETAIL_AMBIGUOUS`, `NONRESPONSE`, timing uncertainty, contradiction, replacement, partial action, and unresolved evidence are adverse or inconclusive, never NA. `NA_NO_ACTION` is not the inherited route `NOACTION`. A record must have exactly one actionability code and exactly one eligibility code; null, empty, or multiple codes fail validation. Panel disagreement does not itself create NA; it remains an explicit compatible adverse/inconclusive state.

The bridge matcher uses the same canonical source-to-panel matcher and preserves all compatible states. An all-`ACTIVE_EXACT` panel result can retain an adverse-compatible state under the inherited shared-error rules. Empty compatible sets emit `OMEGA_EMPTY` and `NO_SELECTION`; they never become consensus.

## 5. Reconciled additive workload ledger

The ledger is additive over actual events but bounded by the inherited fixed maxima. It is not a new budget. Each event receives a globally unique `activity_event_id` and exactly one parent activity, and contains `(subject_id,hadm_id,activity_id,unit_id,reader_id,start,end,minutes,physician_hours,bridge_code,h3_flag,input_manifest_hash,output_manifest_hash)`. `minutes` and `physician_hours` are nonnegative finite values derived from the same start/end or declared machine-time rule; units and rounding are fixed before execution. A shared event is charged once in one activity, never twice within that activity; distinct personnel/processing events may each be charged only when they actually occur and remain within their respective suballocations.

For each admission `i`, compute an additive ledger vector by activity, then reconcile in this order: (1) reject duplicate event IDs or duplicate `(admission,activity,unit,reader,event-kind)` charges; (2) sum event-level actuals without averaging or replacing missing work; (3) check each activity’s inherited per-admission maximum and its bridge/H3 suballocation maximum; (4) sum across admissions and challenges; (5) check global ceilings and atom workload gates. The child preserves the parent maxima: base `2.00 physician hours/50 packet minutes` per selected admission, challenge increment `1.50 hours/50 minutes` per challenge, fixed setup/closeout `120 hours/3,600 minutes`, `N<=900`, `C<=300`, `C<=N`, and global `physician_hours <= 5,070` (therefore below the 5,100 ceiling) and `packet_minutes <=63,600`. The inherited atom gates remain upper physician hours per 100 atom admissions `<=400`, upper median packet time `<=45` minutes, and upper nonresponse/control-infeasibility `<=0.05`.

The bridge/H3 suballocations are ledger partitions, not additions: bridge base at most `0.45 h/13 min` within the five base activities; bridge challenge at most `0.30 h/10 min` within challenge activities; H3 support check at most `0.05 h/2 min` within H3’s `0.35 h/10 min`; serializer/parser/fixtures are within fixed setup/closeout. The ledger writes `ledger_event_manifest.jsonl`, `ledger_activity_totals.json`, and `ledger_reconciliation.json` with event hashes, parent activity, allocation version, actual and maximum totals, uncharged-event count, duplicate count, and arithmetic proof. `bridge_base_actual` and `bridge_challenge_actual` are sums of actual assigned bridge events, not maxima. Any overrun, uncharged event, duplicate charge, event assigned to no parent, activity outside the frozen parent ledger, or challenge without a sampled challenge admission yields `NO_SELECTION` for the affected run; there is no top-up, rescue, re-review, hidden setup, or post-label reallocation.

## 6. Pre-label and verification requirements

Before labels, emit protocol/schema/source manifests, reciprocal unit manifest, canonical DS manifest, availability-search manifest, panel roster, H3 input manifest, allocation table, truth table, matcher codebook, actionability precedence hash, and ledger template. The verifier must test: source and panel row reordering gives identical hashes; exact `U` matching and one-to-many ambiguity; null versus empty versus `UNKNOWN` versus `ABSENT`; `NOT_PRESENT_IN_AVAILABLE_SOURCES` versus `UNKNOWN`; each of the eight availability codes and precedence; duplicate/missing panel keys; two fresh identical H3 runs; changed seed/template/source forcing H3 failure; each actionability precedence collision; additive event reconciliation and duplicate charge rejection; bridge label changes cannot alter pre-label eligibility/atom/route/sample/weight; and zero compatible set, zero denominator, broken seal, or ledger overflow fails closed.

The computational verifier may establish manifest integrity, exact joins, deterministic matching, reproducible reruns, state exclusivity, arithmetic reconciliation, and preservation of frozen population/sample/route inputs. It cannot establish that a radiology assertion is clinically correct, that a clinician saw or acted on it, that `curr_service` identifies responsibility, that a workflow event occurred when it is `NOT_PRESENT_IN_AVAILABLE_SOURCES`, or that any patient benefited. Those claims require image/context adjudication or a prospective within-site silent study recording actual viewing, responsibility, communication, orders/referrals, scheduling, outside care, and outcomes. The only permitted conclusion remains a storage-to-storage, prospective-silent-only documentation/workflow hypothesis with explicit uncertainty.
