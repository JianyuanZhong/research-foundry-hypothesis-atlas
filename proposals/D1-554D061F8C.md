# Do ICU mortality prediction models that use testing-process features learn hospital testing practice rather than patient condition?

A falsifiable, data-bound experiment on eICU-CRD 2.0 (evolved from expert seed eicu-02,
[prior hypothesis]).

## 1. Hypothesis

**H1 (falsifiable):** An ICU-mortality prediction model that includes testing-process
features (M1: lab counts, per-lab missingness indicators, time-since-last-test) degrades
MORE than a value-only model (M0) when transported to held-out hospitals:
Δ_deg = (AUC_in − AUC_out)_M1 − (AUC_in − AUC_out)_M0 > 0 beyond chance.

**H0:** Δ_deg ≈ 0 — testing-process features carry transportable condition information.

## 2. Scientific opening and closest inspected work

Clinical prediction models are increasingly deployed across hospitals, but it is unresolved
whether they learn *patient condition* or *hospital practice*. Laboratory testing process —
which labs are drawn, how often, when the last draw occurred — is strongly site-specific
(data probe: mean 12h lab count per stay ranges 1.8–13.2 across eICU hospitals) and is
routinely available as model input. If models use these features, they may key on the
hospital's testing culture rather than physiology, and should degrade more when transported
to hospitals with different testing practices.

Closest inspected work:
- **[K1] Ploddi et al. 2026** (transportability methodology review) defines a "shortcut
  predictor" as "any predictor that is associated with an outcome and is site-specific" and
  argues excluding such predictors before training is necessary for generalisability. It
  supplies the mechanism hypothesis but is a review: it does not establish that
  testing-process features are shortcut predictors, nor quantify differential degradation.
- **[K2] Hadler et al. 2026** (SafeNET external validation) is the closest empirical
  precedent: a published ML mortality model kept discrimination externally (AUC-ROC 0.87)
  while locally trained models that learned *system-specific EHR patterns, including
  missingness structure*, achieved markedly higher accuracy (AUC-ROC 0.92, Brier 0.04 vs
  0.055). It does not isolate *which* feature family drives the local gain, and uses
  administrative variables in a single receiving system, not laboratory testing process.
- **[K3] Sheikhalishahi et al. 2020** (first multi-centre eICU benchmark; 200,859
  admissions, 208 hospitals) flags multi-centre heterogeneity as a core challenge but uses
  random (not hospital-level) splits and does not test site-shift or testing-practice
  dependence.

**Gap this proposal fills:** none of the inspected works (a) uses testing-process features as
the manipulated variable, (b) compares value-only vs testing-process models on the same
outcome and population, or (c) measures *differential* degradation under whole-hospital
holdout. This proposal makes the [K1] shortcut mechanism falsifiable for a concrete feature
family, using the heterogeneity [K3] flags as the experimental unit, and extends the [K2]
phenomenon from "local vs external model" to a matched M0/M1 head-to-head.

## 3. Population and data bindings (verified against frozen sources)

Dataset: eICU-CRD 2.0 snapshot (SHA-pinned in datasets/eicu/README.md).
- `patient.csv.gz` (200,859 rows): patientunitstayid, hospitalid, age, gender,
  unitdischargestatus, unitdischargeoffset.
- `hospital.csv.gz` (208 rows): hospitalid, numbedscategory, teachingstatus, region.
- `lab.csv.gz` (39,132,531 rows): labid, patientunitstayid, labresultoffset (hours from ICU
  admission), labtypeid, labname, labresult, labresulttext.
- Join keys: lab→patient via patientunitstayid; patient→hospital via hospitalid.
- Time field: labresultoffset (hours, relative to ICU admission); prediction window [0,12] h.

Inclusion (pre-specified, from executed data probe):
1. unitdischargestatus ∈ {Alive, Expired} (34 blanks dropped).
2. ≥1 lab with labresultoffset ∈ [0,12] h → 28,235 stays.
3. Hospital contributes ≥10 such stays → 198 hospitals.
4. Age present (95 dropped).
Analysis population: ≈28,100 stays, 198 hospitals, 5.43% ICU mortality.

## 4. Outcome

ICU mortality: `unitdischargestatus == "Expired"` (10,907/200,859 = 5.43% overall).
Binary outcome at ICU discharge; no time-to-event.

## 5. Features (pre-specified)

Common to M0 and M1:
- Demographics: age, gender.
- Lab values in [0,12] h for 8 key labs (creatinine, glucose, WBC x 1000, platelets x 1000,
  potassium, sodium, pH, BUN — all verified present in ≥4,500 stays): first, mean, last
  (24 value features). Missing → NaN (trees) / median-imputed-with-indicator (logistic).
- apacheApsVar join: default OFF (coverage unverified; a severity summary that would
  dominate the comparison). Decision recorded.
- Lactate: absent from top-30 labnames in this snapshot; dropped rather than substituted.

M1 only (testing-process features, 16):
- T1 total lab rows in [0,12] h; T2 distinct labnames; T3 labs/hour.
- T4–T11: binary "key lab tested in [0,12] h" for the 8 key labs.
- T12a–T12d: time since last test (12 − last offset; 12 if untested) for the 4 most
  prognostic key labs (creatinine, glucose, WBC, platelets).
M1 total: 24 + 3 + 8 + 4 = 39 features.

## 6. Models (baseline vs learned alternative)

- **M0**: (a) logistic regression — simple interpretable baseline; (b) HistGradientBoosting
  — substantive learned alternative that can exploit value×process interactions (xgboost not
  in base environment; HistGB is the available GBM — recorded).
- **M1**: same two model classes with the added testing-process features.
- 2×2 design (feature set × model class): the interaction is the scientific question. The
  GBM comparison reveals whether practice-keying is a linear artifact or a genuine nonlinear
  dependence. Same train/validation splits, same small hyperparameter budget, class weights
  for imbalance.

## 7. Validation scheme (pre-specified)

- **Whole-hospital holdout**: 198 hospitals randomly assigned train (80%) / test (20%),
  fixed seed 42. Test ≈ 40 hospitals, ~4,000–5,000 stays, ~250 deaths. Random draw preserves
  the site-size distribution; sensitivity: 3 additional seeds + leave-5-largest-out variant.
- **In-hospital reference**: AUC on a patient-level 20% holdout within training hospitals
  (no hospital overlap).
- Metrics: AUROC (primary), calibration slope/intercept, Brier, decision-curve net benefit
  at 5/10/20% thresholds.
- **Primary estimand**: Δ_deg per model class, with 1,000 hospital-level bootstrap resamples
  (resample hospitals, not patients) → 95% CI.

## 8. Analysis

1. Fit M0/M1 (logistic + GBM) on training hospitals.
2. Evaluate in-hospital and out-of-hospital.
3. Δ_deg with hospital-level bootstrap CI.
4. Secondary: per-hospital AUC in test hospitals vs that hospital's 12h testing density —
   if M1's per-hospital AUC tracks testing density more strongly than M0's, that is direct
   evidence of practice-keying.
5. GBM feature importance (SHAP if available) for M1.

## 9. Falsification criteria

- **Supportive (H1):** Δ_deg > 0 with 95% CI excluding 0 for ≥1 model class, AND M1's
  per-hospital AUC correlates with hospital testing density more strongly than M0's.
- **Adverse (H0):** Δ_deg CI includes 0 (or Δ_deg < 0) — testing-process features carry
  transportable condition information; the shortcut mechanism does not apply to this family.
- **Inconclusive:** test-set deaths < 200, or |Δ_deg| < 0.005, or in/out AUROC gap < 0.01
  for both models.

## 10. What results would and would not establish

- **Supportive:** testing-process features are partly site-specific shortcut predictors for
  this dataset/outcome; models using them should be recalibrated or feature-pruned before
  cross-hospital deployment. Would NOT establish causality (testing practice → misprediction)
  or that the effect holds for other outcomes (LOS, decompensation) or datasets (MIMIC).
- **Adverse:** testing-process features are condition-informative and transportable; the
  shortcut mechanism may still apply to other site-specific features (unit type, device
  flags) — a different experiment.
- **Inconclusive:** insufficient power or effect too small; motivates a larger holdout or a
  different feature family.

## 11. Limitations

- Observational; no causal claim about testing practice.
- Testing-process features are a proxy for "hospital practice" (lab ordering, not broader
  workflows).
- Single time period (eICU 2014–2015); no temporal drift.
- eICU labname vocabulary is interface-derived and heterogeneous across sites; the 8 key
  labs were chosen by frequency, which may itself reflect common practice.
- Whole-hospital holdout tests a sample of hospitals, not all deployment sites.

## 12. Resource budget (discovery ≠ solver)

- CPU only. Data build: one pass over lab.csv.gz ≈ 136 s measured on 8 cores. Feature matrix
  ≈ 28k × 39 floats. Model fitting < 10 min. Bootstrap 1,000 × 4 models ≈ 30–60 min.
  **Total < 2 h CPU, no GPU.** Solver envelope: same order; no GPU requirement.

## 13. Solver deliverables (what must be fitted/estimated)

- Feature matrix (parquet/csv) with provenance and inclusion audit.
- Per-model in/out AUROC, calibration, Brier, DCA; Δ_deg with 95% CI (4 model×feature
  combinations × primary split + sensitivity splits).
- Per-hospital AUC vs testing-density scatter (M0 vs M1).
- Feature importance for M1-GBM.
- Reproducible script + fixed seeds.
Completion is established by the Δ_deg estimate with CI and the per-hospital AUC-vs-density
comparison, not by any single AUROC.
