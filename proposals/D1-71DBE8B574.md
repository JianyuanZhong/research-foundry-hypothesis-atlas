## Byte-level deterministic unit identity, matching, and serialization

All source parsing and derived artifacts use UTF-8, Unicode NFC normalization, ASCII `LF` line endings, and no locale-dependent operations. Identifiers are serialized as strings exactly as read after trimming only the protocol-declared outer whitespace; numeric identifiers are never converted through floating point. Timestamps are parsed to UTC-naive ISO-8601 strings with six fractional digits when present; null is a distinct JSON `null`, never an empty string or zero. Text is retained byte-for-byte in the source packet; normalization is used only for the locked lexical extractor and never overwrites source text.

### Unit identity

The canonical unit identity is the tuple

```text
U = (subject_id, hadm_id, source_note_id, reciprocal_chain_id, unit_ordinal)
```

where `source_note_id` is `(subject_id,note_id)`, `reciprocal_chain_id` is the deterministic chain identifier produced by the inherited report/addendum parser, and `unit_ordinal` is the zero-based ordinal emitted by the frozen unit extractor within the canonical chain text. If the extractor cannot emit a unique ordinal, the unit is `U_BOUNDARY` and remains in the adverse-compatible set; it is not dropped. `subject_id`, `hadm_id`, and `note_id` are mandatory admission/note key components. No identity may be based on note text, row order, provider/author, or a reviewer’s route.

The extractor consumes only the inherited pre-`D` radiology chain, in chain order determined by the fixed key `(storetime, charttime, note_seq, note_id)` with nulls sorted after non-null values and then by the literal serialized note key. Duplicate physical rows are retained until the source-key audit; duplicate text is not a reason to merge distinct note IDs. A reciprocal restatement is deduplicated only if `U` and the complete locked assertion tuple are identical. Distinct note IDs, chain positions, or ordinals remain distinct units even if all text is equal.

### Assertion representation

Each unit’s route-defining assertion is the exact nine-field tuple

```text
(unit_id, target_cluster, action_modality, due_interval,
 polarity, recipient, responsibility, replacement, conflict)
```

The finite values are the frozen coded value, `ABSENT`, or `UNKNOWN`; no synonym, free-text vote, inferred provider role, or implicit value is allowed. The `unit_id` is the canonical `U` above. `target_cluster` and `action_modality` are emitted only by the predeclared extractor/codebook; an unparseable or ambiguous value is `UNKNOWN`, not a favorable value. `due_interval` is a fixed coded interval, not a guessed calendar date. `replacement` and `conflict` are independent fields; an explicit replacement is never erased because another panel calls the target present.

### Exact matching function

Matching is a pure function of two serialized assertion tuples and the locked unit identities. There is no fuzzy matching, vote, majority, semantic similarity, or analyst override. First require the same admission key and the same target-unit identity where the question is duplicate/restatement; otherwise treat the records as distinct candidate units. For candidate target linkage, compare the five target-defining fields `(target_cluster, action_modality, due_interval, polarity, recipient/responsibility)` under this table:

| comparison | result |
|---|---|
| both values identical coded values | `MATCH` for that field |
| either value is `UNKNOWN` and the other is any admissible value | both `MATCH` and `NONMATCH` states are retained, unless the locked route table makes one impossible; the reason is `UNKNOWN_WILDCARD` |
| one value is `ABSENT`, the other is not `ABSENT` | `NONMATCH` |
| two distinct non-unknown coded values | `NONMATCH` |
| `replacement` or `conflict` differs | retain separate states; never collapse; any unresolved/conflict state is adverse-compatible |

The complete matcher returns an ordered set of states rather than one answer when an `UNKNOWN` creates genuine ambiguity. It returns `DUPLICATE_RESTATEMENT` only for identical `U` and identical complete assertion tuple; otherwise it returns `DISTINCT_UNIT`, `MATCH`, `NONMATCH`, or `AMBIGUOUS_MATCH` with a proof trace. A candidate pair with an unresolved one-to-many mapping is not discarded and is not forced to the most favorable mapping.

### Canonical serialization and hashes

Every derived record is serialized as canonical JSON with these rules: UTF-8; object keys sorted lexicographically; arrays sorted by the declared tuple key; no insignificant whitespace; booleans lowercase; finite numeric values rendered as decimal strings where they are identifiers or probabilities requiring exact arithmetic; no NaN or infinity; and explicit schema/version/protocol fields. The canonical record order is:

```text
(subject_id, hadm_id, source_note_id, reciprocal_chain_id, unit_ordinal,
 target_cluster, action_modality, due_interval, polarity, recipient,
 responsibility, replacement, conflict)
```

The hash is SHA-256 of the canonical UTF-8 byte sequence. The run writes `unit_manifest.jsonl`, `match_manifest.jsonl`, and `serialization_manifest.json` containing schema hash, source hash, protocol hash, code version, input row counts, output row counts, sorted-key assertion, and per-record hash. Re-running extraction twice from the same snapshot must produce byte-identical files and identical manifest hashes. Any ordering difference, duplicate hash with nonidentical key, missing null-vs-unknown distinction, malformed JSON, or source-to-derived row-count mismatch fails closed before labels.

The same serializer is used for route truth-table inputs, compatible-set states, bridge pairs, ledger activity rows, fixtures, and final summary tables. State hashes include all input identities, not merely the resulting route, so two different units that happen to yield `AUTO` cannot collide semantically.

## Label-independent bridge eligibility and explicit coding

The bridge’s eligibility is a pre-label structural predicate. No H1/H2/H3 label, parent route, route result, atom, disagreement, bridge success, or workload outcome may enter eligibility. Eligibility is computed after the frozen source frame and canonical DS selection but before any actionability or bridge reader label.

### Structural eligibility predicate

For an admission `i` and a parent-defined unit `u`, set `BRIDGE_ELIGIBLE(i,u)=1` if and only if all of the following are true:

1. `(subject_id,hadm_id)` is a unique key in `hosp/admissions` and the admission is in the frozen first-eligible adult all-opportunity frame;
2. `u` has a unique canonical identity `U`, belongs to the reciprocal pre-`D` radiology chain, and has `R_store,u` present with `R_store,u < D`; a boundary or unresolved reciprocal chain is not eligible;
3. the unit extractor emits nonempty source text and a complete *structural target envelope* consisting of a target span identifier, action/modality span identifier, and due-interval span identifier. The envelope is a parser output, not an adjudicated assertion of correctness. If the parser cannot locate one of these spans unambiguously, eligibility is `0`, not an actionability failure;
4. the canonical DS exists uniquely for the admission, has nonempty text, and has non-null `note_id` and `storetime`; a missing or nonunique canonical DS is not an eligible bridge pair;
5. the DS-detail join is either uniquely keyed by `(subject_id,note_id,field_ordinal)` after retaining all rows or is explicitly marked `DETAIL_AMBIGUOUS`; detail ambiguity does not delete the pair but makes the applicable bridge result adverse/inconclusive according to the coding table below; and
6. the source-to-DS admission key is exact `(subject_id,hadm_id)`. No subject-only or text-only join is eligible.

The parser, span positions, source hashes, and all failed conditions are written before labels. The parser may be conservative and produce few eligible units. A low eligible count is a feasibility/inconclusive result, never a reason to broaden the parser after labels. The eligibility predicate does not require a particular route or a particular `G_u`, and therefore cannot condition the denominator on the bridge outcome.

A bridge *opportunity* is the ordered pair `(i,u,DS_note_id)` for every structurally eligible unit and its unique canonical DS. All such opportunities are retained in the pre-label atlas. If there are zero eligible units in an atom, the bridge estimand for that atom is `NA_STRUCTURALLY_EMPTY`; it is not zero and does not count as a failed actionability review.

### Actionability and linkage coding after eligibility

For every eligible bridge opportunity, a blinded reader or locked panel records fields independently of route labels. The reader sees the permitted radiology chain, canonical DS, permitted DS detail, and timing/missingness metadata, but not parent labels, routes, atoms, sampling weights, bridge outcomes from another reader, or challenge allocations. The reader does not assign a clinical recommendation or responsible team.

The actionability code is a finite state with the following mutually exclusive hierarchy:

| code | precondition and meaning | estimand treatment |
|---|---|---|
| `NA_NOT_ELIGIBLE` | structural predicate is false: no eligible unit, incomplete parser envelope, absent canonical DS, missing required clock, unresolved chain, or nonunique key | excluded from the eligible-pair numerator and denominator; count and weighted fraction reported separately; never recoded as success/failure |
| `NA_NO_TARGET` | structural pair is eligible but the source unit’s frozen target envelope is explicitly `ABSENT` under the locked parser | not an actionable target; excluded from target-preservation denominator, reported as a prespecified NA subtype |
| `NA_NO_ACTION` | target envelope exists but no action modality is structurally present and the codebook declares the unit outside the actionability construct | excluded from target-preservation denominator; not a route `NOACTION` and not clinical inaction |
| `ACTIVE_EXACT` | eligible unit has a target/action assertion and the DS contains an exact target-linked representation with compatible action and due interval, with no explicit contradiction or replacement | favorable bridge contribution `1` only for exact-preservation estimand |
| `ACTIVE_PARTIAL` | target is linked but one required action or interval field is absent/unknown in DS | adverse-compatible for exact-preservation; retained as partial documentation in a separate descriptive state |
| `SUPERSEDED_EXPLICIT` | DS explicitly documents replacement or conflict for the target | adverse for exact-preservation and actionability; never silently treated as successful propagation |
| `TARGET_CONTRADICTED` | DS explicitly negates or conflicts with the source target/action | adverse |
| `TIMING_UNRESOLVED` | target/action may be present but the due interval or storage chronology needed by the bridge is unresolved | adverse-compatible for route/actionability; bridge timing endpoint is undefined or adverse according to its predeclared denominator |
| `DS_UNREADABLE` | canonical DS text/detail is present in storage but unreadable, malformed, or packet-integrity failed | adverse-compatible, never complete-case deleted |
| `NONRESPONSE` | required reader output absent or malformed | adverse-compatible for upper bounds and reported as missingness |
| `DETAIL_AMBIGUOUS` | duplicate or conflicting detail rows prevent unique interpretation | adverse-compatible; no favorable tie-break |
| `BRIDGE_INCONCLUSIVE` | an eligible pair exists but the locked evidence cannot distinguish the above states | inconclusive/adverse-compatible, not favorable |

`NA_*` is permitted only for the structural predicates and explicit absence states above. It may not be used for a missing reader label, disagreement, unreadable text, timing conflict, or an unfavorable result. Those are adverse or inconclusive. `NOACTION` remains the inherited route state and must never be conflated with `NA_NO_ACTION`.

A complete actionability record therefore contains both `eligibility_code` and `actionability_code`; no single `NULL` field is allowed. For example, an absent canonical DS is `(BRIDGE_ELIGIBLE=0, eligibility_code=NA_NOT_ELIGIBLE, actionability_code=NA_NOT_ELIGIBLE)`, while a malformed reader response for an eligible pair is `(BRIDGE_ELIGIBLE=1, eligibility_code=ELIGIBLE, actionability_code=NONRESPONSE)`. This separation prevents label-dependent denominator changes and prevents adverse cases from disappearing as NA.

### Target-link state machine

The target-linked bridge is computed by a locked state machine applied only after eligibility and label sealing:

```text
NO_ELIGIBLE_PAIR       -> NA_NOT_ELIGIBLE
EXPLICIT_ABSENT_TARGET -> NA_NO_TARGET
EXPLICIT_NO_ACTION     -> NA_NO_ACTION
ELIGIBLE + exact target + exact action + exact due + no conflict
                         -> ACTIVE_EXACT
ELIGIBLE + target + incomplete action/due
                         -> ACTIVE_PARTIAL
ELIGIBLE + explicit replacement or conflict
                         -> SUPERSEDED_EXPLICIT
ELIGIBLE + explicit contradiction
                         -> TARGET_CONTRADICTED
ELIGIBLE + unresolved required time
                         -> TIMING_UNRESOLVED
ELIGIBLE + unreadable/corrupt DS
                         -> DS_UNREADABLE
ELIGIBLE + missing/malformed reader
                         -> NONRESPONSE
ELIGIBLE + unresolved detail multiplicity
                         -> DETAIL_AMBIGUOUS
ELIGIBLE + none of the above can be distinguished
                         -> BRIDGE_INCONCLUSIVE
```

The bridge’s primary secondary functional is the design-weighted proportion of eligible opportunities in `ACTIVE_EXACT` among all structurally eligible target-bearing opportunities, with `NA_NO_TARGET` and `NA_NO_ACTION` reported separately and never silently excluded from the all-opportunity frame. Its companion adverse functional is the design-weighted proportion in the union `{ACTIVE_PARTIAL,SUPERSEDED_EXPLICIT,TARGET_CONTRADICTED,TIMING_UNRESOLVED,DS_UNREADABLE,NONRESPONSE,DETAIL_AMBIGUOUS,BRIDGE_INCONCLUSIVE}`. These are documentation states, not clinical harm states. Exact numerator and denominator contributions are retained per compatible state; no favorable denominator deletion is allowed.

A route-invariant documentation control uses a non-target, non-temporal sentence permutation or provenance-matched nuisance-token transformation. It must retain `eligibility_code`, target envelope, and bridge state. A route-decisive transformation changes exactly one locked target/action/timing field and has a predeclared expected state transition. An infeasible transformation is `CONTROL_INFEASIBLE`, not hand-edited and not removed from the control denominator.
