## Finite-state source-to-panel matcher

The matcher is a pure function of canonical serialized tuples, identities, and declared codebooks. It runs before route labels and before bridge labels. First require exact `(subject_id,hadm_id)`; subject-only or text-only joins are invalid. Identical `U` plus identical complete tuple is `DUPLICATE_RESTATEMENT`. Different note IDs, chain IDs, ordinals, or identities remain `DISTINCT_UNIT` even when text is identical. For the target-defining fields `(target_cluster,action_modality,due_interval,polarity,recipient,responsibility)`, identical coded values are `MATCH`, `ABSENT` versus non-`ABSENT` is `NONMATCH`, distinct coded values are `NONMATCH`, and any `UNKNOWN` retains both `MATCH` and `NONMATCH` branches with reason `UNKNOWN_WILDCARD` unless a frozen truth-table impossibility removes a branch. `replacement` and `conflict` are independent; disagreement or unresolved values are never collapsed.

The executable matcher returns an ordered finite set, not a vote: `DUPLICATE_RESTATEMENT`, `DISTINCT_UNIT`, `MATCH`, `NONMATCH`, `AMBIGUOUS_MATCH`, `U_BOUNDARY`, `KEY_ERROR`, or `MATCHER_ERROR`. `KEY_ERROR` and `MATCHER_ERROR` are adverse-compatible and make the compatible set empty only if no admissible state remains. Each branch records compared fields, branch reason, source and panel identities, and whether it is compatible with the parent truth table. A one-to-many mapping is retained as all compatible branches. An empty branch set emits `OMEGA_EMPTY` and `NO_SELECTION`, never a favorable selection.

## Eight workflow availability states

Workflow availability is a predeclared evidence state, not a clinical or responsibility label and not a route. Compute it before opening H1/H2/H3 or actionability labels from only the inherited source frame, source chronology, and permitted structural packet fields. The exhaustive mutually exclusive codes, evaluated in the listed precedence, are:

1. `WF_AVAILABLE_EXACT`: all required source, admission, unit, canonical-DS, and permitted timing keys exist, are unique, and are internally consistent; the relevant workflow field is present with an exact coded value.
2. `WF_AVAILABLE_PARTIAL`: a permitted workflow field is present, but at least one nonrequired component is absent or `UNKNOWN`; it is usable only with an explicit uncertainty branch.
3. `WF_ABSENT_STRUCTURAL`: the relevant permitted field or record is structurally absent, with no claim that the workflow did not occur.
4. `WF_UNKNOWN_VALUE`: the record exists but its value is null, malformed, unmappable, or semantically unknown under the frozen codebook; it cannot be recoded as absent.
5. `WF_TIMING_UNRESOLVED`: required chronology cannot establish the inherited relation (including missing or contradictory `transfertime`, `intime`, `outtime`, `R_store`, or `D`); preserve the timing branch and adverse compatibility.
6. `WF_CONFLICT`: independently retained source rows or panel representations give incompatible workflow values; no majority or recency tie-break is allowed.
7. `WF_NOT_APPLICABLE`: the atom-defined workflow field is outside scope by a pre-label structural rule; this is distinct from missingness and cannot be used to improve a route.
8. `WF_PACKET_UNAVAILABLE`: the source record exists or is expected by schema, but is not available in the permitted packet/execution lane, or packet integrity/access fails; this is evidence unavailability, not an `ABSENT` clinical fact.

A missing source key, unresolved reciprocal chain, nonunique canonical DS, broken source-to-admission join, or malformed packet cannot be assigned `WF_AVAILABLE_*`. If multiple conditions apply, precedence is `WF_CONFLICT > WF_TIMING_UNRESOLVED > WF_PACKET_UNAVAILABLE > WF_UNKNOWN_VALUE > WF_ABSENT_STRUCTURAL > WF_NOT_APPLICABLE > WF_AVAILABLE_PARTIAL > WF_AVAILABLE_EXACT`, except that a failed required structural predicate also emits the separate eligibility code `NA_NOT_ELIGIBLE`. The full raw condition vector is retained so precedence is auditable. `WF_*` is never converted into `AUTO`, `DEFER`, `NOACTION`, or an actionability code.

## H3 reproducibility certificate

H3 is the inherited assertion-support challenge and remains route-blinded. It receives the frozen source packet and permitted detail, but no H1/H2 output, route, atom, stratum, weights, sample allocation, challenge status, or bridge result. H3 emits an inventory, not a route recommendation: for every visible source unit it records `U`, assertion tuple, target/action/due spans, workflow-availability code, parser/codebook version, and source byte hash. It may emit `UNKNOWN`, `ABSENT`, `CONFLICT`, or `NONRESPONSE`; it cannot infer responsibility or clinical appropriateness.

The certificate `H3_REPRODUCIBLE_EXACT` is emitted only when: (a) the H3 inventory is complete for the sealed packet; (b) every H3 unit matches exactly one pre-label source `U` under the matcher; (c) no source unit is unmatched; (d) every field is either exact coded agreement or an explicitly retained `UNKNOWN` branch; (e) duplicate/restatement handling follows the identity rule; (f) all eight workflow codes and their raw condition vectors are valid; (g) parser, schema, codebook, source, and packet hashes match the seal; and (h) a second deterministic serialization pass is byte-identical. `H3_REPRODUCIBLE_UNKNOWN` is a distinct certificate when the inventory and matching are complete but at least one allowable `UNKNOWN`/ambiguous branch remains. `H3_NONRESPONSE`, `H3_CONFLICT`, `H3_UNMATCHED`, `H3_PACKET_FAILURE`, and `H3_CERTIFICATE_FAILURE` are adverse-compatible or inconclusive as specified by the parent; they never silently become exact reproducibility.

The certificate includes counts by state, unmatched IDs, ambiguous branches, shared-error flags, source/panel hashes, and a signed seal order. H3 is not an oracle: a unanimous H3 result still retains every compatible shared-error state permitted by the parent. A panel can be simultaneously flagged `shared_error` with another panel; shared-error flags are set unions, never mutually exclusive assignments. Compatible sets are built from all panel states and preserve all `UNKNOWN`, `NONRESPONSE`, `CONFLICT`, timing, and boundary branches. No favorable consensus replacement is permitted.

## Sampling, estimands, and fixed workload arithmetic

Execute the parent’s frozen census, five strata, positive inclusion probabilities, deterministic admission draw, sentinel census, formula allocations, pairwise probabilities, challenge reservation, and at-most-900-admission/300-challenge limits exactly. Every sampled admission receives base extraction/QA; every pre-label eligible pair in that admission is processed; no post-label enrichment or new admission is permitted. Bridge estimates remain admission-clustered with inherited admission weights; pair-level rows are descriptive. Exact ratio bounds jointly optimize compatible numerator/denominator states; zero denominator is `UNDEFINED`, not zero.

The parent ledger is the only budget. Let `N` be distinct selected admissions and `C` challenge admissions, with `N<=900`, `C<=300`, `C<=N`. For each admission, charge each actual event exactly once to one immutable parent activity ID. A bridge subevent is additive within that activity’s already declared maximum, not an increment. If a single event serves parent and bridge, it is not double-counted within an activity; separate personnel or processing events have separate IDs and must each fit the relevant suballocation. Required fields are `(subject_id,hadm_id,activity_id,unit_id,reader_id,event_kind,start,end,minutes,physician_hours,bridge_code,source_hash,seal_hash)`.

For every activity `a`, calculate `actual_a = sum(distinct event costs)` and assert `actual_a <= declared_parent_max_a`; calculate bridge-specific actuals as a subset by event ID and assert `bridge_a <= declared_bridge_suballocation_a` without adding it to `actual_a`. Assert the full inequalities before selection:

```text
physician_hours = sum(distinct event physician_hours)
packet_minutes  = sum(distinct event minutes)
physician_hours <= 120 + 2.00*N + 1.50*C
                <= 120 + 2.00*900 + 1.50*300 = 5,070 <= 5,100
packet_minutes  <= 3,600 + 50*N + 50*C
                <= 3,600 + 50*900 + 50*300 = 63,600
N <= 900; C <= 300; C <= N
for each parent activity a: actual_a <= parent_max_a
for each bridge suballocation b: bridge_actual_b <= bridge_max_b
sum(activity actuals) == physician_hours/packet_minutes ledger totals
```

The fixed per-admission parent maxima remain 2.00 physician hours/50 packet minutes for base and 1.50 hours/50 minutes for a challenge increment, with the parent’s declared fixed setup/closeout `120 h/3,600 min`. Bridge maxima remain carved into the listed parent activities (base at most 0.45 h/13 min; challenge at most 0.30 h/10 min) and cannot create a new activity or setup charge. Any overrun, uncharged pair, event overlap, duplicate ID, missing time/cost, negative duration, bridge event outside a parent activity, challenge event without a challenge admission, or equality failure produces global `NO_SELECTION`. Atom-specific workload gates remain unchanged, including upper physician hours per 100 atom admissions `<=400`, upper median packet time `<=45` minutes, and upper nonresponse/control-infeasibility `<=0.05`; bridge burden cannot be pooled across atoms.
